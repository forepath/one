Why this matters

Agents run code nobody has reviewed yet

Most of the time that is fine. But one bad package or one bug is enough to break out onto the server, or to quietly send your code somewhere.

Installing packages

A package can run its own setup script the moment the agent adds it.

Running tests

Tests execute whatever the repository contains, including code the agent just wrote.

Quiet uploads

A script can try to send your code or secrets to a site nobody asked for.

A plain container is a packaging boundary first. Every container on a server talks to the same kernel, so one kernel bug can be enough to get out and reach everyone else.

The isolation stack

Five layers, each covering a different risk

  1. 1

    No admin rights

    The agent works as a normal user and cannot install system software or change the machine.

    stops: taking over the environment
  2. 2

    A sandbox around the code

    Its own container, a separate sandbox kernel, or a small virtual machine of its own.

    stops: breaking out onto the server
  3. 3

    A checkpoint around the network

    A web proxy, a DNS filter and a firewall decide which connections may leave.

    stops: leaks and attacks on your network
  4. 4

    Limits on data

    Secrets stay hidden, and agents only see their own workspace, often only after asking.

    stops: reading what it shouldn't
  5. 5

    Rules and a record

    Central rules nobody can quietly weaken, and an audit log plus alerts for every decision.

    stops: silent changes
No single layer has to be perfect. Where one ends, the next one takes over. The rest of the deck goes through them one by one.

Tested on every server

Tested, not assumed

A level is only offered after the server has started real test environments on it and every check passed. Something merely being installed never counts.

Testing the sandboxed level

  1. The sandbox is installed and can be started
  2. The test really runs inside the sandbox
  3. Files can be written, renamed, read and deleted
  4. Commands run, also as a normal user
  5. Output and errors are captured
  6. Traffic still goes through the network checkpoint
  7. All of it within 90 seconds

Inside the checkpoint

A proxy, a name filter and a firewall

Each part handles one kind of traffic. Requests that ignore the proxy settings are caught anyway, and nothing is decrypted.

Closed from the start: the checkpoint starts first and blocks everything until its rules are loaded.
Deny beats allow, and a broken rule set never replaces the last one that worked.
Fits your company proxy: allowed traffic can be passed on, so your own controls see it too.

Judging by name has a limit

A site can hide behind the name of a big shared provider. Short allow lists, blocking raw addresses or offline mode close that gap. Because agents have no admin rights, they cannot dodge the name filter either.

This is why the checkpoint is a separate container: the agent cannot reach its settings, even if the agent's own environment were fully compromised.

Keeping data apart

Isolating data, not just code

A sealed box is only half the job. What an agent can read and what it can say matters just as much.

Secrets out of sight

Passwords and keys are stored encrypted and handed over in a protected file, never as settings other tools could read.

Only its own workspace

An agent can look up tickets and knowledge of its own workspace, and nothing else, with a pass tied to the current chat.

It asks first

Before reading a full document in a chat, the agent asks you. Automations are allowed, hidden runs are denied.

Messages are filtered

Every message in and out is checked. Filters can hide secrets, rewrite parts or flag something for review.

Handoffs stay inside

Agents can pass work to each other, but only within the same workspace.

Shared files are read-only

Attachments and shared folders can be read, but an agent cannot change them.

These limits hold no matter which isolation level the environment runs on. Two things never enter the box at all: deployment credentials, because the control plane talks to your CI itself, and graph data, because the agent server builds an environment's code graph outside the container.
