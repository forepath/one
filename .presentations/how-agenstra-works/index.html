Architecture overview

How Agenstra works, from the first prompt to the last packet

One central service decides what is allowed. Servers next to your code do the work. Every agent gets its own sealed-off environment, and nothing leaves it without passing a checkpoint.

Control plane Isolated environments Network checkpoint Layered rules
Agenstra is where teams run, govern and ship with coding agents on infrastructure they own. This walk-through follows one request from the browser to the last packet that leaves the environment. Use the arrow keys or Space to advance, N for notes.

The big idea

Agenstra separates deciding from doing

One part knows who you are and what is allowed. The other part runs the agents and enforces those decisions right next to the work.

Decides

Control plane

Signs people in, works out the rules, keeps tickets, knowledge, deployments and the audit log, and sends every request to the right server.

The control plane always calls out

Does the work

Agent servers

Each server runs the agents' environments, checks how strongly it can isolate them, filters messages and records every network decision.

environmentsisolationfiltersnetwork checks

Connections go one way

The control plane connects out to each server. Servers only need to accept that one connection.

Requests and live updates

Ordinary requests for data, and a live connection for chat, terminals, the remote desktop and boards.

Secrets stay out of sight

Passwords and keys are stored encrypted and handed to an agent in a protected file, never as visible settings.

The single most important idea: decisions are made centrally, enforcement happens next to the work. Because the control plane always dials out, a server never needs to reach back into it.

Sandboxing

Four isolation levels, never a silent downgrade

Agent code is code nobody has reviewed yet. So Agenstra can put a second, separate kernel between it and your server: a sandbox kernel (gVisor), or a whole virtual machine.

The dot is a request from the agent to the operating system. With a plain container it goes straight to the server's kernel. In the sandbox it is answered by the sandbox kernel, and only a few safe requests reach the server. In a microVM it lands in the virtual machine's own kernel.

The scene cycles through the four modes. Off: nothing is filtered. Watch: everything passes, but what would have been blocked is recorded. Enforce: the lists apply. Offline: nothing leaves, but console, chat and files keep working.

Where filtering stops

What the checkpoint can see, and what it cannot

Plain web trafficunencrypted HTTP

Encrypted web trafficHTTPS

Name lookupsDNS
Name askedAnswer
Everything elseblocked unless allowed
Address and portContent

Nothing is decrypted

Encrypted traffic is judged by the site name alone. The agent never has to trust a special certificate.

Closed from the start

The checkpoint starts before the environment and blocks everything until its rules are loaded.

No side doors

Unusual protocols are blocked, internal networks too. A deny rule always beats an allow rule.

Fits your company proxy

Allowed traffic can be sent on to your own proxy, so your existing controls still see it.

Judging by name has a limit

A site can hide behind the name of a big shared provider. Short allow lists, blocking raw addresses or offline mode close that gap. And because agents run without admin rights, they cannot dodge the name filter.

Being honest about limits is part of the design: every control says where it ends and what covers the gap.

A sandbox is not a virtual machine

It shrinks what an attacker can reach on the server a lot, but it is not a full wall. Where you need one, use the microVM level.

no admin rightsnetwork checkpoint

The sandbox costs some speed

Calculations run at nearly full speed. Installing packages and building big projects is slower, and a few low-level tools don't work.

standard level per agent, on record

A microVM takes a moment to start

It boots its own kernel first, a few seconds, and needs a little extra memory. The server must support hardware virtualization.

tested per serverfails safe
