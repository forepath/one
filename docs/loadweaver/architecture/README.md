# Architecture Overview

```
 Console / CLI / API  ──►  Control plane (API, policy compiler, Postgres + TimescaleDB, etcd)
                                 │  desired state per node (revisioned, NOTIFY to every replica)
                                 ▼
                 one outbound gRPC stream per node (mutual TLS, node identity from the cluster CA)
                                 ▼
 Node agent (TypeScript, single executable, systemd) ──► WireGuard · BIRD · nftables · DNS · Docker
```

## Control plane

- Runs on 1 to 5 designated nodes (the control-plane members). Below three nodes it runs on whatever exists; with two nodes an optional witness provides the third vote.
- State lives in Postgres managed by Patroni (streaming replication, automatic leader failover) with etcd as consensus store (each member's Patroni talks to its own etcd member, so joining or leaving members never restart Postgres). The API reaches the current leader through a local proxy on every member.
- **Postgres role passwords:** `LOADWEAVER_POSTGRES_REPLICATION_PASSWORD` sets the password of the members' replication role (`standby`) and `LOADWEAVER_POSTGRES_ADMIN_PASSWORD` that of Spilo's `admin` role; when unset, each is derived per cluster from `ENCRYPTION_KEY` (HKDF) at push time and sent only to members over their authenticated stream. The leader's agent sets a changed value on the existing roles itself (in a session that logs no statements, only a SCRAM verifier goes to the server), since Spilo sets them only when it creates a data directory.
- Members start with any number of nodes up, without split brain: agents report whether they hold etcd data (`heartbeat.etcd`, stored as `etcd_member_since` per node). While no voter holds data, the control plane lets exactly one connected member bootstrap a new etcd cluster of itself (the first by name, `controlPlane.etcd.bootstrap`); every other member with an empty data directory joins through the voters holding data (`controlPlane.etcd.peers`) once one is reachable and never bootstraps on its own. Nobody bootstraps while a connected voter hasn't reported since it connected. A member whose etcd can't start yet reports the failed `control-plane` step (and the revision's `error`) while the rest of its desired state applies; it doesn't confirm a new release until its role is up.
- **Database of an external control plane** (the compose stack of the built-in setup): it starts on its own Postgres. As soon as the first real member's Patroni leader answers (`GET :8008/primary` over the overlay), it **hands the database over**: writes are frozen (mutating API requests get `503` "…moving its database…", the external database is set read-only and its sessions are reconnected), the members get database `DB_DATABASE` owned by `DB_USERNAME` (Spilo's superuser from the replicated environment), the schema comes from the same migrations, the data is copied in one snapshot (`row_to_json` → `json_populate_recordset`, sequences, row counts verified), and the control plane restarts onto the members through an in-process leader proxy (`127.0.0.1:5433`, TLS verified against the cluster CA). The target is kept in `database-target.json` on the control-plane state volume (no credentials); the row `lw_database_handover` (`external` / `handover` / `members`) travels with the data, so both databases agree. Audited `control-plane.database-handover`. Until then the members' role says `controlPlane.database: pending` and their API replica stays stopped (etcd, Patroni, log store, object store and registry run).
  - **External copy:** the external Postgres then follows as a logical-replication subscriber (`lw_external_copy`: tables with a primary key; no hypertables, no migration bookkeeping). The handover switches the members to `wal_level = logical` through Patroni (`ignore_slots` for the copy's slots) before the freeze. New migrations run on the members, then on the external copy, then the subscription refreshes.
    - **Failover-safe slot** (decision 2026-10-31): the subscription's slot is a **Patroni permanent logical slot** (`PATCH /config` `slots: {lw_external_copy_<id>: {type: logical, database, plugin: pgoutput}}`, earlier copy slots removed, `hot_standby_feedback: on`). Patroni copies it to the replicas and advances it there, so after a failover the new primary continues from its copy and the subscription goes on without a re-copy (changes since the copy's last advance are sent again and skipped by the subscriber's origin). Each sync records the primary and which members hold the slot (`external_copy.leader` / `slotHolders`); a new primary that held no copy got the slot created afresh by Patroni (changes in between would be missing), which counts as lost.
    - **Re-copy that keeps the copy** (only when the slot is really lost, apply errors last 10 min, tables stay copying for 10 min, or the subscription was left disabled mid-copy): the old subscription is only disabled; a new slot is created over a replication connection with an exported snapshot; the published tables are copied from that snapshot into the external tables in **one transaction** (`DELETE` + insert, so readers and a takeover keep the previous rows until it commits); then the subscription is re-created on the new slot with `copy_data = false`. A failed re-copy drops its slot and leaves the previous copy untouched.
    - **"Complete as of":** `external_copy.completeAt` is the last sync that found every table in sync and said `ok`, carried through later `syncing` / `error` reports. The subscription connects with `sslmode=require` (the external server has no copy of the cluster CA), so the external Postgres must reach the members' overlay addresses on 5432. `LOADWEAVER_DATABASE_EXTERNAL_COPY=off` skips it.
  - **All registered members unreachable** (no primary for 45 s): new connections go to the external copy with read-only sessions, writes get `503` (`code: read-only`, "the cluster's database members are unreachable; read-only until one is back"; `code: freeze` during a handover). A primary answering again ends it.
    - **Background jobs while writes can't happen** (read-only fallback, handover freeze, no member primary yet): every write-only job (VM commands, Git sync / bot, VM image imports, SIEM forwarding, cron / workload / object-store / public-address / DNS / import controllers, autoscaler, backups and platform backups / copy / cut-over / DR, usage, certificates, metrics roll-up / retention, live recordings / orphaned sessions, rollouts, update policies, drafts, audit mirror, remote access, migration sessions, apply sweep) checks `writesPaused(job)` (`database-target.runtime.ts`) at the start of its tick and skips it. Each job logs once when it pauses and once when it resumes; skipped ticks only at debug level. Reads the console needs (health, alerts, nodes, overview) are evaluated live.
    - **Built-in control-plane member:** its registration and heartbeat (`lw_builtin_members`) are kept in memory while the database can't take writes, so it stays `ok` (its key opens the master key under the 3.39 rules, the key-mismatch guard works from what can be read) and are written on the first heartbeat once it can.
  - **Fenced takeover** (decision 2026-10-31): after `LOADWEAVER_DATABASE_TAKEOVER_AFTER_MS` (default 120 000; `0` / `off` keeps it read-only) without any member primary, the control plane promotes its external copy if it is **usable**: the subscription exists (also disabled while a re-copy builds the next copy) with every table synchronized (`srsubstate = r`), the replicated `lw_database_handover` row says `members`, and the copy was last confirmed complete (`external_copy.completeAt`, replicated through the subscription itself) at most `LOADWEAVER_DATABASE_TAKEOVER_MAX_LAG_MS` (5 min) before the members went away. It drops the subscription (`slot_name = NONE`; the members' slot stays), runs the migrations on the copy, moves every owned sequence past its column's maximum (logical replication doesn't carry sequences), marks the row `external` with a new **fencing epoch**, `taken_over_at` and a new Patroni scope for members starting empty (`<cluster>-t<epoch>`), writes the target file and restarts onto it. Audited `control-plane.database-takeover`; critical inbox item (kind `database`) until a handover re-seeds the members. Otherwise it stays read-only and says why: `GET /api/cluster` → `controlPlane.database` (`readOnlyReason`, `readOnlySince`, `takeover {afterMs, state, reason, noPrimarySince}`, `epoch`, `takenOverAt` (only while the database is on the external side because of that takeover; the fence info keeps it after a handover), `postgresScope`, `fences`), plus a critical inbox item.
  - **Fencing:** the epoch grows with every takeover and every handover; it is in `lw_database_handover.epoch` of each database and in the members' role (`controlPlane.databaseFence {epoch, takenOverAt, scope}`, feature `database-fencing`). The control plane never switches to, copies into or drops a member primary whose data has an older epoch: it fences it at the database level (`ALTER DATABASE … SET loadweaver.fenced_epoch / fenced_at / fenced_scope`, `default_transaction_read_only = on`, client sessions cut) and waits until only one current primary answers before a handover; on the members' target a second, older primary is fenced the same way. The member's agent probes its own Postgres (python in Spilo: the row's epoch and the fence settings) on applies (≤ 1/min) and every minute; data older than the highest epoch it has seen (persisted in `<state>/database-fence.json`) is fenced: API replica stopped, rows with `created_at` / `updated_at` / `time` after the takeover exported as NDJSON per table (+ `manifest.json`; time series skipped, ≤ 200 000 rows per table) to `<state>/database-diverged-<time>/`, Spilo stopped, the data directory **moved** to `<state>/postgres.fenced-e<epoch>-<time>` (never deleted), an empty one started in the takeover's scope. The next handover re-seeds the members (new epoch) and the external copy subscribes again. The agent reports the fence in its heartbeat (`databaseFence`); the control plane records it once (row `fences`, audit `control-plane.database-fenced`, warning inbox item for a week). Exported rows are never merged. A role with a lower epoch than one the agent has seen (a member replica on fenced data) is not applied.
  - **No registered member left** (removed / `left`, the master key's `r = 0` rule): the subscription is dropped, the external copy becomes the database again (restart, audited `control-plane.database-return`); the next real member gets a fresh handover.
  - **On-node installs** never do any of this: the agent marks member API replicas with `LOADWEAVER_CONTROL_PLANE_ON_MEMBER=true` (older agents: the API connects to the leader proxy `127.0.0.1:5433`). `LOADWEAVER_DATABASE_HANDOVER=off` keeps an external control plane on its own database (old behaviour; member API replicas then start without a database).
- The **API is the source of truth** for desired state. Every declarative change goes through plan → apply.
- The **policy compiler** turns groups and policies into the configuration of every enforcement layer, per node, and stores it as a revisioned desired state.

## Node agent

- A TypeScript Node.js single executable application, run by systemd outside Docker: it manages Docker and the host network and keeps working while Docker is restarted.
- Opens one persistent, outbound stream to the control plane. Nodes need no inbound management port; nodes behind NAT work.
- Applies desired states layer by layer (tunnels → routing → filtering / services → DNS → control-plane role). If a layer fails, the previous state is re-applied and the report says exactly what happened.
- Owns only what carries its prefix: `lw-*` WireGuard interfaces, the `lw0` loopback, the `inet loadweaver` and `inet lw_live` (debug tunnels) nftables tables, the `lwbr0` workload bridge. Foreign tunnels and firewall rules stay untouched.

## Agent protocol versioning

The control plane is updated before the nodes, so it must keep serving agents one release behind (N-1). Every message schema stays strict on the agent; instead, both sides negotiate what may be sent:

- The agent's `hello` carries `protocolVersion` (an integer, currently `2`) and `features`, the optional protocol features it implements. Agents built before versioning send neither and count as version `0` without features. Feature ids the control plane doesn't know (a newer agent) are ignored.
- New control-plane → agent fields are always optional and gated by a feature. New message types are gated the same way. Every message to a node passes one place on its stream, which strips the fields and drops the message types gated by features the node didn't advertise. An N-1 agent therefore never receives a field or message it would reject. Fields whose absence would weaken a workload (an isolation level, device access, a microVM) are **refused** instead of stripped: the message isn't sent at all, the node keeps its previous desired state, and the built-in alert `builtin:node-protocol-refused` fires (the scheduler doesn't place such workloads on those agents in the first place).
- New agent → control-plane fields are optional, so N-1 agents that don't send them stay valid; fields an N-1 agent sends are never removed while it may still be connected. While control-plane members update one by one (3.26), an updated member's agent may talk to a control plane one release behind: the control plane therefore ignores agent fields it doesn't know (everything it knows stays strict), and unknown message types are answered `rejected` without closing the stream.
- On every release, the current schemas are frozen as JSON Schema snapshots (the next release's N-1 protocol). Contract tests check the current protocol against the latest snapshot: new fields towards the agent without a feature gate, new enum values, removed or newly required fields fail the build. The integration tests also check that everything the control plane sends to a version-0 agent is valid against the snapshot.

## Identity

- Every cluster has its own certificate authority. Nodes get certificates with the identity `spiffe://<cluster>.loadweaver/node/<name>`; the control plane decides the identity, not the request.
- Node certificates rotate automatically when less than a third of their lifetime is left. A node that leaves loses its identity immediately.
