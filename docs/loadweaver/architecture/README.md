# Architecture Overview

```
 Console / CLI / API  ──►  Control plane (API, policy compiler, Postgres + TimescaleDB, etcd)
                                 │  desired state per node (revisioned, NOTIFY to every replica)
                                 ▼
                 one outbound gRPC stream per node (mutual TLS, node identity from the cluster CA)
                                 ▼
 Node agent (TypeScript, single executable, systemd) ──► WireGuard · BIRD · nftables · DNS · Docker
```

## Control plane

- Runs on 1 to 5 designated nodes (the control-plane members). Below three nodes it runs on whatever exists; with two nodes an optional witness provides the third vote.
- State lives in Postgres managed by Patroni (streaming replication, automatic leader failover) with etcd as consensus store (each member's Patroni talks to its own etcd member, so joining or leaving members never restart Postgres). The API reaches the current leader through a local proxy on every member.
- The **API is the source of truth** for desired state. Every declarative change goes through plan → apply.
- The **policy compiler** turns groups and policies into the configuration of every enforcement layer, per node, and stores it as a revisioned desired state.

## Node agent

- A TypeScript Node.js single executable application, run by systemd outside Docker: it manages Docker and the host network and keeps working while Docker is restarted.
- Opens one persistent, outbound stream to the control plane. Nodes need no inbound management port; nodes behind NAT work.
- Applies desired states layer by layer (tunnels → routing → filtering / services → DNS → control-plane role). If a layer fails, the previous state is re-applied and the report says exactly what happened.
- Owns only what carries its prefix: `lw-*` WireGuard interfaces, the `lw0` loopback, the `inet loadweaver` and `inet lw_live` (debug tunnels) nftables tables, the `lwbr0` workload bridge. Foreign tunnels and firewall rules stay untouched.

## Agent protocol versioning

The control plane is updated before the nodes, so it must keep serving agents one release behind (N-1). Every message schema stays strict on the agent; instead, both sides negotiate what may be sent:

- The agent's `hello` carries `protocolVersion` (an integer, currently `2`) and `features`, the optional protocol features it implements. Agents built before versioning send neither and count as version `0` without features. Feature ids the control plane doesn't know (a newer agent) are ignored.
- New control-plane → agent fields are always optional and gated by a feature. New message types are gated the same way. Every message to a node passes one place on its stream, which strips the fields and drops the message types gated by features the node didn't advertise. An N-1 agent therefore never receives a field or message it would reject.
- New agent → control-plane fields are optional, so N-1 agents that don't send them stay valid; fields an N-1 agent sends are never removed while it may still be connected. While control-plane members update one by one (3.26), an updated member's agent may talk to a control plane one release behind: the control plane therefore ignores agent fields it doesn't know (everything it knows stays strict), and unknown message types are answered `rejected` without closing the stream.
- On every release, the current schemas are frozen as JSON Schema snapshots (the next release's N-1 protocol). Contract tests check the current protocol against the latest snapshot: new fields towards the agent without a feature gate, new enum values, removed or newly required fields fail the build. The integration tests also check that everything the control plane sends to a version-0 agent is valid against the snapshot.

A feature is advertised by an agent only once it implements it: agents advertise `live-migration` since the agent side exists (checkpoint manager on runc / CRIU, mutual-TLS transfer endpoint, agent-managed restored replicas, kept-address network plugin); older agents don't, and their replicas move blue / green or by short stop. Hellos may also report checkpoint support (`capabilities.checkpoint`: `runc`, `runsc`, CRIU version) and an estimated transfer rate (`capabilities.transferBitsPerSecond`).

Further protocol features (backups, ...) are added by the steps that introduce them, under the same rules.

## Identity

- Every cluster has its own certificate authority. Nodes get certificates with the identity `spiffe://<cluster>.loadweaver/node/<name>`; the control plane decides the identity, not the request.
- Node certificates rotate automatically when less than a third of their lifetime is left. A node that leaves loses its identity immediately.
