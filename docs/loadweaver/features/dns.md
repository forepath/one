# DNS

Loadweaver manages DNS records like everything else: as desired state, shown in the plan, applied through **DNS providers**. Ingress hostnames get their records automatically; other records are declared as resources.

```yaml
apiVersion: loadweaver.com/v1
kind: DnsProvider
metadata: { name: cf }
spec: { type: cloudflare, credentials: 'secret://infra/cloudflare' }
---
apiVersion: loadweaver.com/v1
kind: DnsZone
metadata: { name: example }
spec: { zone: example.com, provider: cf }
---
apiVersion: loadweaver.com/v1
kind: DnsRecord
metadata: { name: mail }
spec: { zone: example, name: '@', type: MX, values: [mx.example.net], priority: 10 }
```

The plan shows changes in words, e.g. "creates A shop.example.com → 203.0.113.10 at cf (zone example.com)". Record types: A, AAAA, CNAME, TXT, MX, SRV, CAA, NS, PTR.

## Ownership

Next to every name it manages, Loadweaver keeps a TXT marker (`_loadweaver.<name>`) with the cluster id and the record types it owns there. Records it doesn't own are never changed or deleted; they show up as conflicts on `GET /api/dns/zones`. This makes adopting an existing zone safe.

## Providers

| Type         | What it is                                                                                                                                   |
| ------------ | -------------------------------------------------------------------------------------------------------------------------------------------- |
| `cloudflare` | Cloudflare's API (more providers come as plugins via `DYNAMIC_DNS_PROVIDERS`)                                                                |
| `bind9`      | name servers hosted on the cluster: on a node group (default: the control-plane members), every instance gets the zones pushed directly      |
| `axfr`       | external name servers reached by zone transfers with TSIG: `servers: [...]`, `credentials:` the base64 TSIG secret, `tsigAlgorithm` optional |

### Hosted bind9

bind9 answers authoritatively only: no recursion, and no transfers except to configured secondaries. It applies response rate limiting and validates every zone before serving it. Name servers need public addresses: the nodes' own, or anycast addresses from a pool:

```yaml
spec: { type: bind9, nodeGroup: dns, nameServers: { pool: anycast, count: 2 } }
```

The plan warns when a zone has fewer than two name servers or all of them are in one site.

## Multi-provider zones

A zone has one primary and optional secondaries:

- **API secondaries** (e.g. Cloudflare) get the same records through their API.
- **AXFR secondaries** pull the zone from hosted bind9, authenticated with TSIG and notified on every change.
- **An external primary** (`axfr` as `provider`) owns the zone; hosted bind9 pulls it as secondary. Records for such a zone are added at that primary, so the plan rejects declaring them here.

The control plane compares the secondaries' serials with the primary's. Drift shows on `GET /api/dns/zones` and as a plan warning.

## DNSSEC

Opt in per zone on hosted bind9:

```yaml
kind: DnsZone
spec:
  zone: example.com
  provider: ns # bind9
  secondaries: [ext] # AXFR only: they receive the signed zone
  dnssec: true
  registrar: { type: <plugin>, credentials: 'secret://infra/registrar' } # optional
```

- Keys are generated by the control plane, stored encrypted and pushed to every bind9 instance, so all of them sign with the same key; bind9 signs.
- `GET /api/dns/dnssec` lists the DS records to publish at the parent. A registrar plugin (`DYNAMIC_REGISTRAR_PROVIDERS`) publishes them for you; bind9 also publishes CDS / CDNSKEY for parents that read them.
- Keys roll over every year, but only once the current key's DS is at the parent. During a rollover both keys stay published until the new DS is visible at the parent; the old key goes 14 days after its DS left.
- Turning DNSSEC off keeps the zone signed until no DS is left at the parent, then serves it unsigned.

API secondaries would serve the zone unsigned, so the plan rejects them for signed zones.
