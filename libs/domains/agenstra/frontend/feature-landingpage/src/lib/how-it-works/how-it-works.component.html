How Agenstra works, from the first prompt to the last packet

A control plane that decides and agent managers that execute. Every environment runs in its own container, can run inside a gVisor sandbox, and reaches the internet only through its own egress guard.

Six moving parts, one clear chain of command

Agenstra separates deciding from doing. The control plane knows who you are and what is allowed. The hosts run the agents and enforce those decisions right next to the workload.

Egress guard

A small sidecar per environment that owns the worker's network. DNS lookups and web requests pass through it and are checked against your policy.

Identity and access

Single sign-on through Keycloak, built-in users or API keys. Workspace roles decide who may see, chat with and change which environments.

OIDC JWT scoped tokens

Connections go one way

The controller connects out to each agent manager, and managers never call back. Hosts only need to accept connections from the control plane.

REST and live events

HTTP for state, WebSockets for chat, terminals, desktop streams and boards. Both share one port per service.

Secrets stay out of sight

Credentials are encrypted at rest and reach a worker through a root-only volume, not container variables that show up in a docker inspect.

What happens when you send a prompt

The same six steps apply whether a developer types in the console or a ticket automation starts an autonomous run. Each step has an owner, and each leaves a trace.

  1. 1

    Sign in and authorize

    You authenticate with single sign-on, a built-in account or a scoped token. The controller checks your role in the workspace before anything reaches a host.

  2. 2

    Resolve the policy

    Global, workspace and environment configuration are merged into one effective policy: models, tools, permissions, web traffic and message filters. It is synced to the host.

  3. 3

    Filter the message

    Message filters check every message in both directions. A rule can drop it, rewrite matches or flag it for review. When several rules match, the most restrictive one wins.

  4. 4

    Work in the environment

    The agent reads and edits the cloned repository, runs commands and tests, and opens a browser if it needs one. All of it inside its own container, optionally on gVisor.

  5. 5

    Reach out, within limits

    Package installs, API calls and Git pushes leave through the guard. Each connection is allowed, blocked or, in monitor mode, observed against the web traffic policy.

  6. 6

    Record and notify

    The controller pulls filter hits and traffic decisions into the audit log and can send signed webhooks, so your security tooling sees what the agent did.

Three isolation levels, never a silent downgrade

A regular container shares the host kernel with everything else on the machine. Agent code is code you have not reviewed yet, so Agenstra can put a second kernel in between: gVisor.

Probed, not assumed

Each host proves with real test containers what it can run: at startup, every six hours and on demand.

Fails closed, overrides are on record

If the sandbox cannot start, the environment is not created. Choosing a weaker level needs a confirmation and is recorded with the person who chose it.

Runs on ordinary cloud VMs

gVisor's systrap platform needs no KVM or nested virtualization. Hosts with hardware virtualization additionally run gVisor on KVM. Provisioned hosts get both installed and verified automatically.

Where a system call ends up

Standard

runc
  1. Agent and its tools
  2. Host kernel namespaces, cgroups, seccomp

Docker's default. Available on every host. Choose it for workloads that need Docker-in-Docker, eBPF, io_uring or KVM.

Sandboxed

runsc
  1. Agent and its tools
  2. gVisor Sentry Linux implemented in user space
  3. Host kernel small, filtered set of calls

Preselected wherever the host is ready. A kernel exploit has to break the Sentry first before it can reach the host.

Sandboxed + KVM

runsc-kvm
  1. Agent and its tools
  2. gVisor Sentry in a hardware-virtualized address space
  3. Host kernel small, filtered set of calls

Preselected where the host exposes KVM. System calls trap into the Sentry through the CPU's virtualization extensions instead of seccomp.

One guard per environment, and nothing gets around it

The worker does not have a network of its own. It joins the network namespace of its egress guard, the only container allowed to change firewall rules. Requests that ignore proxy settings are intercepted anyway.

No TLS decryption

HTTPS is decided on the server name of the handshake. Nothing is decrypted and the agent does not have to trust an extra certificate.

Locked down first

The guard blocks everything before its policy loads, and it exists before the worker does. An invalid policy never replaces the last one that worked.

No side doors

QUIC, DNS over TLS and undeclared protocols are denied. Private networks are blocked by default. Deny rules always win over allow rules.

Fits your corporate proxy

If your network requires a proxy, the guard forwards allowed traffic to it. Your existing controls still see every request.

Policy flows downhill

Security sets the floor once, globally. Workspaces and environments can add to it but never take anything away, so a new team cannot opt out of what everyone agreed on.

The same heredity covers models and providers, MCP servers, permissions, web traffic and message filters. Lock a whole section on a higher layer and lower layers cannot touch it at all.

  1. Global

    Platform and security teams: approved models, blocked hosts, mandatory message filters.

  2. Workspace

    Team leads: the package registries and APIs this team needs, inside what global allows.

  3. Environment

    One agent: narrower still, for example offline for a sensitive repository.

No single layer has to be perfect. Where one control ends, the next one takes over.

gVisor is not a virtual machine

It shrinks the host kernel's attack surface considerably, but it is not a full virtual machine. Where the host supports KVM, the Sentry is additionally isolated by hardware virtualization. It works together with unprivileged workloads, the egress guard and a hardened host.

Mitigated Non-root workloads Egress guard

The sandbox costs some speed

CPU-bound work runs at near-native speed. Dependency installs and builds that touch many small files are noticeably slower than on the standard level.

Mitigated Standard level per environment, on record

HTTPS filtering trusts the name

Without decryption, domain fronting on shared CDNs and encrypted client hellos cannot be told apart by name. Narrow allowlists, blocked IP literals or offline mode close that gap.

Mitigated Narrow allowlists Blocked IP literals Offline mode

Non-root matters

A process with root rights inside a worker could bypass the DNS policy, though not the web rules. That is why workers run as an unprivileged user without sudo.

Mitigated Non-root workloads No sudo
