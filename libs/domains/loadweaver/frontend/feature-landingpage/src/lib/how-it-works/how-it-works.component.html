How Loadweaver works, from the first policy to the next failover

A control plane that plans and a node agent on every server that applies. Everything you change is declarative YAML, every change is a plan, and every connection exists only because a policy allows it.

Groups, and policies between them

Everything else builds on this. Nodes and workloads join groups, and a policy grants one group access to another, the way security groups work in the cloud. No policy, no connection.

Node groups

Decide which nodes share a network, which get tunnels to each other and which routes are exchanged.

Workload groups

Services join by label, independent of the node they run on, so a rule stays valid when a workload migrates.

Selectors

Membership by selector, such as site = fra1, role = ingress or runtime = sandboxed. Rights add up across all groups.

Built-in groups

internet, cluster, control-plane and one group per site. Platform traffic is a built-in policy too, so it cannot be broken by accident.

The control plane compiles each allow rule into every layer it affects

  • Tunneling

    WireGuard peers only exist between nodes that need to talk, with AllowedIPs limited accordingly.

  • Routing

    BIRD only exchanges the prefixes of groups that are allowed to talk.

  • Filtering

    Stateful nftables rules on each node, so return traffic is allowed automatically.

  • Proxy (L7)

    Hostname, URL and SNI rules in Envoy, with mTLS between the node proxies and deny wins inside L7.

  • Exposure

    Ingress and port forwards: "internet" is a group, and exposing a service is an allow from it.

What happens when you change something

The same steps apply whether you click in the console, run the CLI, call the API or push to Git. The control plane is the source of truth; all of them create plans against it.

  1. 1

    Describe what you want

    YAML, the same language as Docker Compose, with a JSON Schema for editor validation. The UI writes the same YAML.

  2. 2

    Get a plan

    The difference between desired and actual state, with the compiled effect per layer and every DNS record it creates.

  3. 3

    Read the failure analysis

    Every single point of failure is listed with its cause, plus the capacity left after losing a node.

  4. 4

    Lock only what changes

    A plan locks the deployments, groups, policies or nodes its diff touches. Unrelated plans run in parallel.

  5. 5

    Apply, or roll back

    Failed or cancelled applies roll back on their own. If a rollback fails, you see the real state and a proposed fix-forward plan.

  6. 6

    Heal or report drift

    What the platform owns is healed automatically. Changes made outside Loadweaver become a proposed plan, never silently overwritten.

No single host failure takes an app down

For every deployment, the plan simulates the loss of each single node and each site and checks whether data, deployment and traffic survive.

The failure domain is the node by default. Surviving the loss of a whole site is an opt-in per deployment or cluster, available from three sites, and validated by the same analysis.

The analysis keeps running after the apply: when a replica is lost or a node degrades, the cluster shows as at risk on the map and in notifications until redundancy is restored.

Pinning is allowed, and visible

You may tie something to one host on purpose. The plan warns about it up front, and you acknowledge it with a reason in the config.

  • Data

    A volume without replicas, replicas only on one node, or bind mounts to host paths.

  • Deployment

    A placement selector that matches one node, one replica without failover, or device access.

  • Traffic

    A failover IP that only one node may hold, or a policy whose only allowed path runs via one node.

Ingress that fails over on its own

Which nodes may hold a failover IP is a node group. When the holder goes down, the IP moves to a healthy member, using whatever your environment supports.

DNS failover where an IP cannot move

  • Modes: failover to ordered backups, healthy multi-value answers, weighted answers and geo or latency steering.
  • Endpoints are probed from at least two sites; a switch needs a quorum of probes and the control plane, so one isolated site cannot flip records on its own.
  • Hysteresis against flapping and automatic fail-back after a stable period, or manual fail-back per hostname.
  • Failover records get a low TTL of 30 seconds by default. The plan shows the expected recovery time and is honest that DNS failover is slower and fuzzier than a floating IP.

DNS under the same plan

  • Records are desired state: ingress hostnames create their records, and the plan shows the DNS diff per provider.
  • Cloudflare or bind9 hosted in the cluster, behind one provider interface. Loadweaver only touches records it owns, so existing zones can be adopted safely.
  • Zones with a primary and secondary providers, and opt-in DNSSEC with automatic key rollovers for hosted zones.
  • Every switch is an event on the timeline, in the audit log and raises an alert.

Configuration in Git, if you want it

Everything can be done in the UI, and everything that is configuration can also live in Git. UI and Git are two editors of the same YAML.

Two ways to combine them

Git is authoritative and UI edits open a pull request, or bidirectional and Loadweaver commits UI changes back with plan id and author. Conflicts show in the plan.

No secrets in the repo

YAML only holds secret references. SOPS-encrypted files are optional, and plaintext secrets in a push are rejected.

Your Git host

GitHub, GitLab, Gitea / Forgejo and plain Git over SSH or HTTPS, triggered by webhooks or polling, per cluster or per project.

GitHub & GitLab

A plan bot in your pull requests

Opening or pushing to a pull request plans automatically. One sticky comment shows the plan diff, pins and failure analysis warnings, quota and capacity impact, image scan results, drift and locks held by other pull requests. A status check links to the plan on the map.

Comments trigger actions, merging does nothing

  • Applies run on a comment, once the pull request is mergeable and the approval rules are met.
  • Touched resources stay locked until the pull request is applied, closed or unlocked.
  • After a successful apply the bot merges the pull request, so the default branch matches what runs.
