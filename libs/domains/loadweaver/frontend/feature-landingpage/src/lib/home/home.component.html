High availability for the servers you already have

Loadweaver starts where small fleets are: a handful of nodes, often spread across sites. You get a cluster that survives the loss of a server, without the overhead of running Kubernetes, and it grows with you to around 1,000 nodes per cluster.

Start with one node, grow when you need to

A single node is already a complete setup. Nodes can join and leave over and over again: growing from one to many and shrinking back is a normal operation, not a migration project. When a node leaves, it is drained first, and nothing is dropped without your choice.

One node to start. More sites when you need them.

Encrypted network between your sites

Every node runs the network itself. Nodes connect across sites over WireGuard, and routes between them are exchanged with BIRD, so your sites behave like one cluster.

Tunnels only where needed

WireGuard peers exist only between nodes that a policy lets talk to each other.

Addresses that follow

Every service gets a stable IP and DNS name that moves with it when it migrates.

Policy-aware discovery

Cluster DNS only answers for services the caller is allowed to reach.

Shared storage on every node

Volumes are replicated at block level and show up in Docker as a volume plugin. Stateful workloads stay available when a node goes down, from a single node upwards.

Sync nearby, async far away

Synchronous within a site, asynchronous across sites, configurable per volume.

Loss you can see up front

Losing a node loses no data; for losing a site, the plan shows the bounded loss as RPO.

Placement as a policy

For example two synchronous replicas in one site and one asynchronous replica in another.

Ingress that fails over on its own

When the node holding a public IP goes down, the IP moves to a healthy node. Where an IP cannot move, DNS failover takes over. Web traffic and TCP / UDP port forwards are both covered.

Fits your environment

Floating IP on a shared network, BGP announcements, or your provider's failover IP API.

Certificates already there

Built-in ACME; certificates sit on every ingress node, so a failover never waits on issuance.

Limits that hold everywhere

Cluster-wide rate limits, connection limits for port forwards and an optional WAF per hostname.

Everything is a policy

Routing, tunnels, filtering and exposure exist only because a policy allows them. Policies connect groups, like security groups in the cloud, and stay valid when a workload moves to another node.

Deny by default

Nothing talks across groups unless an allow rule says so, and rules are never transitive.

One rule, every layer

An allow rule is compiled into tunnels, routes, firewall rules, the proxy and ingress for you.

Monitor before you enforce

Roll out a policy in monitor mode and see what it would block before it blocks anything.

See every change before it happens

Every change produces a plan: the difference between what you want and what runs, reviewed and then applied. Like Terraform, for your whole cluster.

Failure analysis built in

The plan simulates the loss of every node and site and lists each single point of failure.

Locks that stay out of the way

A plan locks only what it touches, so unrelated changes run in parallel.

Rollback and drift

Failed applies roll back on their own. Changes made outside Loadweaver are reported, never overwritten.

Everything is observable

A live map of every site, node, workload, tunnel and volume, with the traffic between them. Every log the platform produces is one click away.

Live, timeline and plan

Watch traffic live, scrub back through a failover, or overlay a pending plan on the map.

All logs, one query

Containers, proxy, firewall, routing, tunnels and ingress, correlated by deployment, node and policy.

Trace any path

Pick a hostname and see how a request is routed right now, with every policy it passes.

Built around the Docker Compose files you already have

Docker is the base. A deployment is a Compose project, and Loadweaver settings live in extension fields, so the same file still works with plain docker compose.

compose.yaml with Loadweaver extensions (example) x-loadweaver 
{{ composeExample }}

Migration without drama

Every Compose deployment can move between nodes: live where eligible, blue / green where replicas allow, a short stop otherwise. A failed live attempt falls back without data loss.

Pins are explicit

Pinning data, a deployment or traffic to one host is allowed, but the plan warns about it up front. You acknowledge a pin with a reason in the file.

Git if you want it

Everything works in the UI. Connect a repository and pushes create plans, with a plan bot for GitHub and GitLab pull requests.

From containers to full VMs

Each service picks its isolation level, up to a microVM booted from the same image. Full virtual machines with replicated disks and live migration run alongside, planned like everything else.

Capacity kept honest

Every service has CPU and memory requests. The plan warns when the remaining nodes could not take over after a node loss.

Know what breaks before anything breaks

No single host failure takes an app down, unless you pin something to that host on purpose. The plan checks this for every deployment before you apply.

It shows the effect per layer, the DNS records it creates, the capacity left after a node loss and every single point of failure with its cause. The same analysis keeps running afterwards and flags the cluster as at risk until redundancy is back.
